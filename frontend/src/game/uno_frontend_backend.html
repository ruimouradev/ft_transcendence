Uno - o protocolo do jogo

O jogo vive num websocket por sala, em wss://<site>/ws/game/{sala}. O cliente envia ações ("quero jogar esta carta") e, depois de cada jogada aceite, o servidor envia a todos o estado completo do jogo - tudo JSON em texto. Este documento lista essas mensagens nos dois sentidos; a definição oficial está em backend/app/game/contract.py.

00 · A vida de uma sala

Antes do dicionário, o filme. Uma sala nasce, enche, joga, esvazia e morre, e cada momento tem as suas regras.

Entrar tem duas portas no mesmo ecrã: a lista das públicas (o GET /api/rooms da secção 01) e o campo de código para as privadas. O código é inventado por quem cria a sala, viaja no endereço do websocket (/ws/game/{codigo}) e é ao mesmo tempo convite e chave, como no Among Us. Convém que viva no endereço da própria página (tipo /game/ABC123) enquanto se está lá dentro: assim um F5 sabe onde voltar.

Quem joga tem conta: ficou decidido em equipa que só se joga com login feito - o ecrã só deixa chegar ao jogo quem tem sessão aberta, e o cookie dela viaja sozinho no handshake do websocket, a identificar a pessoa. O token do welcome continua a existir como chave de reconexão.

No lobby, quem manda é o host (o host_id do estado, sempre um humano) e só dele o servidor aceita o start e os bots. Entra-se com join enquanto há lugar. Sair é fechar o websocket, sem mensagem nenhuma: o lugar liberta-se, a lista encolhe para todos, e se saiu o host a coroa passa sozinha ao humano seguinte. Uma sala só com bots fecha-se.

O start só é aceite com a sala cheia (o max_players escolhido no create, bots a contar). A ideia de UX combinada: mostrar "waiting for the room to be full 3/4" e libertar o botão do host quando encher.

Durante o jogo já ninguém entra e sair é diferente: o lugar fica guardado, cinzento (connected: false), com a mão à espera no servidor. Quem tem login volta ao lugar só com um join (o cookie identifica-o), convidados voltam com o token do welcome. A mesa nunca muda de tamanho nem de ordem a meio de um jogo.

E ninguém congela a mesa: cada vez tem um relógio de 60 segundos no servidor. Se o jogador da vez não mexer (adormeceu, saiu, ou é um bot sem AI), a vez fecha-se sozinha: sem jogada possível na mão, ou a dever cartas de um +4 ou de uma pilha de +2, compra o que devia e segue; com jogada possível, perde simplesmente a vez. O ecrã fica a saber pelo last_action com kind timeout (entra no próximo merge do ws).

No fim, o host pode carregar em play again, que é simplesmente outro start: jogo novo do zero, com quem ficou. A sala morre quando fica sem humanos, e o código liberta-se para quem o quiser reutilizar.

O exemplo a andar, numa sala de 3 lugares:

AconteceO que o servidor manda a todos
A cria a sala de 3estado com [A], phase lobby
B entraestado com [A, B]
C entraestado com [A, B, C], sala cheia
B carrega em sair (o browser fecha a ligação) estado com [A, C]
A mete um bot no lugar vago estado com [A, C, Bot 1], cheia outra vez
A carrega em start estado com phase playing, cartas na mão

Repara no padrão: aconteça o que acontecer, a resposta é sempre um estado novo com a sala como ela ficou. O ecrã não gere nada, recebe estado e desenha estado.

01 · O que envias (ações)

create - abrir uma sala

{ "type": "create", "name": "ana",
  "settings": { "hand_size": 7, "stacking": false, "seven_zero": false,
                "max_players": 4, "public": false } }

Cria a sala e o criador fica logo sentado como primeiro jogador. settings é opcional: omitido = regras oficiais, sala privada de 4 lugares. As opções ficam fixas para o jogo todo (é isto que o formulário do "Create Game" envia; é a parte da UI do módulo de customization). Com public: true a sala aparece na lista de salas enquanto estiver em lobby.

join - entrar numa sala

{ "type": "join", "name": "ana" }
{ "type": "join", "name": "ana", "token": "abc123..." }

A primeira forma pede um lugar novo - a sala tem de existir (o join já não cria salas, isso é o create) e estar em lobby com lugar livre (o limite é o max_players dela). A segunda é o rejoin: com o token que recebeste no welcome, recuperas o teu lugar e a tua mão depois de uma queda de ligação, mesmo a meio do jogo. E se a pessoa tiver feito login no site, nem do token precisa: o servidor reconhece-a pelo cookie e devolve-lhe o lugar só com o join simples.

add_bot e remove_bot - bots no lobby

{ "type": "add_bot" }
{ "type": "remove_bot", "target": "b1" }

Só para o host e só no lobby. O add_bot senta um jogador AI na próxima cadeira livre (conta para o max_players); o remove_bot tira o bot com aquele id. Os bots aparecem no players como jogadores normais, com nomes "Bot 1", "Bot 2"... Dá para jogar sozinho contra bots ou em mesas mistas.

start - começar a partida

{ "type": "start" }

Só o host pode - e o host é sempre o primeiro humano da lista de players, nunca um bot. A sala tem de estar cheia (o max_players escolhido no create, com bots a contar), senão o servidor recusa. Baralha, dá as cartas e vira a primeira carta da mesa. E o mesmo start num jogo acabado é o play again: o jogo renasce do zero com quem está na sala, e se entretanto saiu alguém a sala volta ao lobby à espera de encher.

play - jogar uma carta

{ "type": "play", "card": "c42" }
{ "type": "play", "card": "c42", "color": "red" }
{ "type": "play", "card": "c42", "uno": true }
{ "type": "play", "card": "c42", "target": "p3" }
CampoQuando
cardSempre: o id da carta (vem na tua mão, em you.hand)
colorObrigatório quando a carta é wild: a cor escolhida ("red", "yellow", "green", "blue"). Vai na própria jogada - não existe uma segunda mensagem para a cor.
unoDizer UNO também viaja na jogada: true na carta que deixa o jogador com apenas 1. Sem isso, fica sujeito ao catch dos outros.
targetSó para um 7 com a regra seven-zero ativa: o id do jogador com quem trocar de mão.

draw - comprar

{ "type": "draw" }

Três significados, o servidor sabe qual é: compra normal (1 carta; se ela for jogável a vez continua tua para a jogares ou passares), aceitar um +4 pendente (comes as 4 e és saltado), ou comprar uma pilha de +2 acumulada. Só uma compra normal por turno.

pass - passar

{ "type": "pass" }

Só válido depois de comprares uma carta jogável e decidires não a jogar. (Sem teres comprado, não podes passar - no Uno ninguém passa de graça.)

challenge - desafiar um +4

{ "type": "challenge" }

Só para a vítima de um +4 pendente, em alternativa ao draw. Se quem o jogou tinha carta da cor ativa na mão (bluff): ele é que come as 4 e tu jogas normalmente. Se o +4 era limpo: comes 6 (4+2 de castigo) e és saltado.

catch - apanhar quem não disse UNO

{ "type": "catch", "target": "p3" }

Qualquer jogador pode, a qualquer momento, contra quem está com 1 carta e não disse UNO: o apanhado compra 2. Não podes apanhar-te a ti próprio.

a lista de salas (HTTP, fora do socket)

GET /api/rooms

[ { "code": "A7F3", "host": "ana", "players": ["ana", "Bot 1"],
    "max_players": 4,
    "settings": { "hand_size": 7, "stacking": false, "seven_zero": true,
                  "max_players": 4, "public": true } } ]

Devolve as salas públicas que ainda estão em lobby com lugar livre - as privadas, as cheias e os jogos a decorrer nunca aparecem, portanto tudo o que a lista mostra é entrável. players é a lista dos nomes de quem lá está (bots incluídos), e o "2/4" faz-se contando os nomes. O resto alimenta o ecrã da lista: o código para o botão de entrar, quem criou, e as opções da sala para mostrares o "Default/Custom Game". Atenção ao caminho: esta rota vive em /api/rooms, sem o /api/v1 da plataforma (é do servidor do jogo), portanto pede-se com axios ou fetch diretos e não com o cliente que tem o /api/v1 no baseURL.

02 · O que recebes

welcome - o teu lugar

{ "type": "welcome", "id": "p1", "token": "abc123..." }

Chega uma vez, quando te sentas. O id é como apareces no estado; o token é a tua chave de rejoin - guarda-o e usa-o no join se a ligação cair.

state - o jogo completo, da tua perspetiva

Chega a todos depois de cada jogada aceite (cada um recebe a sua versão: a tua mão vai só para ti, dos outros só vês contagens). A UI redesenha a partir do último recebido - não há deltas nem replay.

Durante o lobby o estado é o mesmo mas quase vazio: a mão e o playable vêm vazios, turn e top_card a null - o que interessa nessa fase é o players, quem já entrou e está à espera do start.

{ "type": "state", "seq": 17, "phase": "playing",
  "you": { "id": "p1",
           "hand": [ { "id": "c42", "color": "red", "value": "7" }, ... ],
           "playable": ["c42", "c51"],
           "drawn": null },
  "players": [ { "id": "p1", "name": "ana", "cards": 5,
                 "connected": true, "uno": false, "bot": false,
                 "points": 0 }, ... ],
  "host_id": "p1",
  "settings": { "hand_size": 7, "stacking": false, "seven_zero": false,
                "max_players": 4, "public": false },
  "top_card": { "id": "c13", "color": "blue", "value": "4" },
  "active_color": "blue", "direction": 1, "turn": "p1",
  "draw_pile": 34, "stack": 0, "plus4_by": null,
  "last_action": { "player": "p2", "kind": "draw", "card": null },
  "winner": null, "winner_score": null }
CampoSignificado
seqCresce a cada atualização; um estado atrasado reconhece-se por ter seq menor que o último recebido.
phase"lobby" (sala de espera), "playing" (jogo a decorrer), "finished" (há vencedor).
you.handAs tuas cartas. Cada uma tem id único, cor ("red"/"yellow"/"green"/"blue"/"wild") e valor ("0"-"9", "+2", "skip", "reverse", "wild", "+4").
you.playableOs ids das cartas que o jogador pode jogar neste momento, já calculados pelo servidor com as regras todas. Vazia = não há jogada possível na mão.
you.drawnO id da carta acabada de comprar, enquanto ainda pode ser jogada ou passada.
playersTodos, na ordem da mesa (a ordem é fixa). cards = quantas têm; connected = se a ligação dele está viva; uno = se disse UNO; bot = se a cadeira é de um bot; points = valor da mão no fim do jogo (0 durante).
host_idQuem manda na sala (start e bots). É sempre um humano; se o host sair, o campo passa sozinho ao seguinte. Serve, por exemplo, para decidir a quem mostrar esses botões.
settingsAs regras da sala, sempre no estado: quem entra por código ou volta de um F5 fica a saber o mesmo que quem veio da lista. Serve, por exemplo, para o lobby mostrar as opções e o "3/4" (o max_players vem cá dentro).
top_cardA carta no topo da mesa.
active_colorA cor que conta agora - é esta que decide o que combina, e depois de um wild difere da cor da carta do topo.
direction1 ou -1, o sentido da roda.
turnO id de quem joga; null fora do "playing".
draw_pileCartas no monte de compra (quando esgota, o servidor rebaralha o descarte sozinho).
stackCom o stacking ativo: cartas acumuladas na pilha de +2 que o jogador da vez deve. >0 = ele ou responde com outro +2 ou compra tudo com draw.
plus4_byId de quem jogou um +4 que ainda não foi respondido. A vítima (quem está em turn) tem duas saídas: draw aceita as 4, challenge desafia.
last_actionO que acabou de acontecer: quem (player), o quê (kind: join, start, play, draw, pass, catch, challenge, timeout) e a carta, quando ela ficou pública. O timeout é o servidor a fechar uma vez adormecida, nunca vem de um jogador: numa compra forçada chegam dois estados seguidos, um draw e depois o timeout, para poderes animar os dois.
winner / winner_scoreNo fim: quem ganhou e a pontuação (a soma das cartas que sobraram aos outros; os points de cada player dão o ranking - menos pontos = melhor classificado).

error - jogada recusada

{ "type": "error", "code": "INVALID_CARD",
  "msg": "card matches neither color nor value" }

Vai só para quem errou; o estado não muda e mais ninguém vê nada. O code é estável (bom para traduzir); a msg é em inglês para debug.

CódigoQuando
NOT_YOUR_TURNJogada fora de vez
INVALID_CARDA carta não combina com a mesa; ou há pilha de +2 e isto não é um +2; ou depois de comprar só a carta comprada é válida
COLOR_REQUIREDWild sem cor escolhida
TARGET_REQUIRED7 (seven-zero) sem alvo
CARD_NOT_IN_HANDId que não está na mão
INVALID_CATCHO alvo disse UNO, não tem 1 carta, ou tentaste apanhar-te a ti
INVALID_CHALLENGENão há +4 para desafiar
ROOM_NOT_FOUNDJoin com um código que não corresponde a nenhuma sala
ROOM_FULLSala cheia, não há lugar
GAME_NOT_STARTED / GAME_ALREADY_STARTEDAção na fase errada, incluindo o join a um jogo a decorrer (sem token nem login)
INVALID_MESSAGEJSON malformado, tipo desconhecido, e casos como "só o host começa", "compra ou desafia o +4 primeiro", "a sala já existe" (create repetido), "a sala não está cheia" (start cedo demais) ou "só o host mexe nos bots"

03 · O que o estado já traz calculado

Alguns campos existem para a UI não ter de calcular nada. O que fazer com eles é contigo - ficam alguns exemplos de uso possível:

  • you.playable - as cartas jogáveis naquele momento, já com as regras todas pesadas pelo servidor. Serve, por exemplo, para iluminar essas cartas, ou para filtrar cliques antes de enviar - em qualquer dos casos, sem escrever uma única regra do Uno em TypeScript.
  • you.drawn - o momento em que o jogador comprou uma carta jogável e ainda pode decidir. Um exemplo clássico: aparecer a escolha "jogas ou passas?".
  • plus4_by - há um +4 à espera de resposta. É a informação para, por exemplo, a vítima ver as duas saídas (comprar ou desafiar).
  • stack - quantas cartas a pilha de +2 já acumulou (com o stacking ligado). Dá, por exemplo, para um aviso "deves X cartas".
  • last_action - quem fez o quê, com a carta quando ela ficou pública. É a matéria-prima natural para animações, se as quiseres.
  • players[].uno e players[].connected - se alguém disse UNO e se está ligado, por exemplo para badges.
  • points e winner_score - no fim do jogo, a informação do ranking vem feita: a pontuação do vencedor e os pontos que sobraram a cada um (menos = melhor).

04 · Como o servidor se comporta

O ciclo de vida de uma sala, do princípio ao fim:

  • Entrada: a primeira mensagem de um socket tem de ser join ou create - qualquer outra coisa antes disso é respondida com "create or join first". A sala nasce no create, aceita jogadores até ao max_players dela e só enquanto está em lobby (o join numa sala que não existe dá erro).
  • Durante o jogo: cada jogada aceite gera um broadcast - todos recebem o estado novo, cada um com a sua versão (a mão de cada jogador só vai para ele, os outros recebem contagens; o baralho nunca sai do servidor). Uma jogada recusada não gera broadcast nenhum: só o autor recebe o error e mais ninguém percebe que algo foi tentado.
  • Ordem: o seq de cada estado é sempre crescente, por isso um estado atrasado reconhece-se por ter seq menor que o último recebido.
  • Sair e quedas de ligação: para o servidor são a mesma coisa, a ligação fechou (um botão de sair é só fechar o websocket, não há mensagem). O que muda é a fase: no lobby o lugar liberta-se a sério - a lista encolhe, e se saiu o host o humano seguinte herda a coroa sozinho. Em jogo o lugar fica guardado, marcado como desligado (os outros veem pelo connected), e nada se perde - o jogo continua e a mão fica à espera. Um join com o token do welcome (ou só com o cookie, para quem tem login) devolve o mesmo lugar, e o servidor reenvia logo o estado atual: a reconexão não precisa de repor nada.
  • Validação: todas as ações passam pelas regras no servidor - nada de ilegal entra no jogo, venha de onde vier. Podes usar o playable para nem deixar tentar, ou simplesmente enviar e tratar o erro; as duas abordagens funcionam.
  • Play again: no fim de um jogo, um novo start do host reconstrói tudo do zero com quem ficou na sala - baralho novo, mãos novas, mesmo código. Quem saiu de vez perde o lugar nessa altura; se a sala ficou por encher, volta ao lobby à espera (e enche-se com bots ou gente nova).
  • Fim: a sala morre quando fica sem humanos - no lobby quando o último sai (bots não seguram salas), em jogo quando todos estão desligados ao mesmo tempo. Salas diferentes são jogos completamente independentes.
Se algum campo ou ação te fizer falta, ou se quiseres alterar alguma coisa, diz - muda-se no contract do servidor e combinamos os dois lados.
